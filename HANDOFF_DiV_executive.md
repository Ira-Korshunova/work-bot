## 1. Project Overview

### 1.1. Что это за продукт

**DiV_executive** — Telegram-бот-ассистент по внешнеэкономической деятельности (ВЭД) для малого и среднего бизнеса. Бот принимает четыре типа входных данных и возвращает структурированный результат:

| Режим | Вход | Обработка | Выход |
|---|---|---|---|
| Документ | фото/скан/PDF коносамента, инвойса, пакинг-листа | Tesseract OCR + классификация типа документа | извлечённые поля документа |
| Товар | фото товара | мультимодальная модель Qwen-VL | структурированный JSON (бренд, модель, категория, цена и др.) |
| Голос | голосовое сообщение | Yandex SpeechKit STT/TTS | распознанный текст / озвученный ответ |
| База ВЭД (RAG) | текстовый вопрос | гибридный RAG (BM25 + FAISS + реранк) → LLM | ответ по нормативной базе со ссылками на источники |

### 1.2. Целевой пользователь

Специалист отдела ВЭД / логист / владелец малого бизнеса, который:
- разбирает входящие транспортные и коммерческие документы (коносаменты, инвойсы, пакинг-листы) и хочет автоматизировать их «расшифровку»;
- проверяет товар по фото (учитываемые категории, валютные метки, характеристики);
- присылает голосовые вопросы и получает ответы голосом же (удобно в дороге/на складе);
- задаёт вопросы по нормативной базе ВЭД (таможенное оформление, валютный контроль, Инкотермс 2020, ТН ВЭД/ЕАЭС, документы для международных сделок) и получает ответ с цитатой из источника.

### 1.3. Ключевая ценность (почему бот осмыслен)

1. **Экономия времени на рутинном разборе документов.** OCR-классификация и извлечение 15–25 полей (номер, стороны, порты, судно, стоимость, условия) вместо ручного ввода.
2. **Ответы по нормативке «с доказательством».** RAG-режим отвечает строго по загруженной базе нормативных документов и даёт ссылку на источник `[источник: <файл>, <заголовок>]` — это защищает от галлюцинаций и позволяет юристу проверить ответ.
3. **Снижение стоимости vs крупные модели.** Рекомендуемые модели семейства Qwen (DashScope) в разы дешевле GPT-класса на тех же задачах OCR и извлечения структурированных данных; OCR — локальный и бесплатный (Tesseract).
4. **Единая точка входа на знакомой платформе Telegram** — не требует обучения пользователя интерфейсу.

## 2. Prompt Engineering Guide (ключевые промпты)

Ниже — два главных промпта, от которых зависит корректность работы. Оба живут в коде, а не в конфиге: вносить правки — править исходники и перезапускать бота.

### 2.1. Системный промпт RAG «База ВЭД» — `rag_engine.py`

**Где:** константа `RAG_SYSTEM_PROMPT` (строки ~123–140) и шаблон `RAG_PROMPT_TEMPLATE` (~142–147).

**Роль:** задаёт, что модель — юрист-консультант по ВЭД, обязана отвечать **только по контексту**, не выдумывать, выдавать ответ в plain-text формате Telegram (без markdown) и добавлять дисклеймер.

**Текущие параметры генерации** (из `rag_engine.py` / `.env`):
- `RAG_CHAT_MODEL` = `qwen3-vl-flash` (не `qwen-plus` — тот упирается в квоту 403);
- `RAG_TOP_K` = 5 (сколько кандидатов в финальный контекст);
- `RAG_MAX_CONTEXT` = 6000 символов (обрезание контекста перед запросом);
- `RAG_SIM_THRESHOLD` = 0.30 (гейт косинус-сходства dense-поиска);
- `RAG_RERANK_ON` = 1, модель `qwen3-rerank`;
- verify-проверка grounded: `VERIFY_MIN_GROUNDED_SCORE = 0.6`.

**Ключевые инструкции в промпте:**
- отвечать СТРОГО на основе «КОНТЕКСТ» в запросе; иначе дословно: «По имеющейся базе ответа не нашёл…»;
- формат plain-text для Telegram: списки дефисами/цифрами, без `#`, `**`, `*`, `` ` ``, `>`;
- при нескольких источниках — использовать все и пояснить, чем они дополняют друг друга;
- финальный дисклеймер «Не является юридической консультацией».

**Когда работает хорошо:** вопрос по загруженной базе нормативных документов с чёткой формулировкой (термины, названия документов, номера статей).

**Когда работает плохо (ограничения):**
- **Вопрос вне базы** → обязан вернуть «не нашёл»; если этого не происходит — проблема в ретривер-гейтах или в том, что источник ещё не добавлен и не переиндексирован.
- **Сложный многосоставной вопрос** — контекст может не покрыть все части; ответ становится частичным.
- **Числовые/сроковые значения** — чувствительны к квотам модели и обрезке контекста; если модель смениться, сроки могут «поплыть».
- **Вопросы, требующие актуальных на сегодня правил** — бот отвечает по статичной загруженной базе; изменения нормативки требуют добавления документа и `/ingest`.

**Практика правки:** добавлен новый документ → положить в `rag_data/docs/` → переиндексировать (`/ingest` или `python3 rag_engine.py ingest`) → проверить `python3 rag_engine.py query "вопрос"`. Не менять промпт «на глаз» без прогона eval-набора (`python3 rag_engine.py eval`).

### 2.2. Vision-промпт распознавания товара — `agent_vision.py` (класс `VisionProductAgent`)

**Где:** строка ~90, передаётся вместе с image-блоком в `qwen3-vl-flash` (`max_tokens=500`).

**Роль:** просит модель вернуть только JSON с полями `brand, model_name, category, price, currency, color, material, dimensions, weight, specs, description`; при наличии ценника/этикетки — извлечь цену, баркод/SKU — в `specs`; вернуть только валидный JSON без markdown.

**Когда работает хорошо:** чёткое фото товара с читаемым текстом (этикетка, ценник, логотип), хорошее освещение, товар в кадре.

**Когда работает плохо:**
- размытое/тёмное изображение, частичное перекрытие, мелкий или искажённый текст → цена/модель не извлекаются (поля `null`);
- товар в упаковке без видимой маркировки → категория определяется грубо;
- несколько товаров в кадре → модель может смешать характеристики в одно описание.

### 2.3. Сопутствующий промпт: проверка «обоснованности ответа» (`_verify_answer_grounded`, `rag_engine.py` ~856–887)

Дополнительный «промпт-проверяющий», который оценивает от 0 до 1, основан ли ответ на контексте (`temperature=0.0, max_tokens=10`). Порог `0.6` — если ответ не основан, он отбраковывается. Это ключевая защита от галлюцинаций, поэтому **не отключать** (`RAG_ANSWER_VERIFY=1`).

## 3. Метрики успеха и риски/ограничения

### 3.1. Технические метрики

| Метрика | Целевое значение | Как мерить |
|---|---|---|
| Валидность JSONL/ответа Vision | 100% запросов возвращают парсимый JSON | json-парсинг ответа агента после обрезки markdown-обёрток |
| Валидность ответа RAG (grounded) | verify-оценка ≥ 0.6 | `RAG_ANSWER_VERIFY` + лог `Answer grounded score` |
| Retrieval recall (retrieval_recall) | ≥ 0.9 | eval-набор, `python3 rag_engine.py eval` |
| Keyword hit (kw_hit, BM25) | ≥ 0.9 | eval-набор |
| Pass rate eval-набора (16 вопросов) | ≥ 15/16 | `rag_engine.py eval` |
| Честный отказ вне базы | 100% (нет галлюцинации) | вопрос вне базы → «не нашёл» |
| OCR-классификация типа документа | ≥ 90% верно (BL/Invoice/Packing/Unknown) | ручной контроль на эталонных сканах |
| APDEX / время ответа | интерактив: RAG-ответ ≤ 30–60 с | тайминги в логах (`REQUEST_TIMEOUT=60`) |
| Доступность бота | 99%+ (KeepAlive через launchd) | мониторинг `bot_launchd.err/out`, uptime |

### 3.2. Бизнес-метрики

| Метрика | Смысл | Источник данных |
|---|---|---|
| Охват пользователей (юзеры/чаты) | число активных пользователей | `work_bot.db` (таблицы `sessions`, `interactions`) |
| Количество успешных сессий по режимам | востребованность Документ/Товар/Голос/База | таблица `interactions.type` |
| Доля вопросов, получивших ответ (не «не нашёл») | полезность RAG | лог `handle_rag_qa` |
| Время экономии на документе | снижение ручного ввода при извлечении полей | качественно, по числу извлечённых полей |
| Стоимость на 1 обработку | контроль бюджета (токены/сек/символы) | тарифы DashScope + Yandex (см. таблицы в `DiV_executive_MVP.md`) |

### 3.3. Ключевые риски и ограничения (2–3 основных)

1. **Галлюцинации и устаревание нормативной базы.** Ответы RAG корректны только по мере актуальности загруженных документов и порога grounded-проверки. Если в базу не добавлен новый нормативный акт или порог `VERIFY_MIN_GROUNDED_SCORE` снижен/выключен — риск выдачи неточного или выдуманного ответа растёт. Митигация: регулярная переиндексация при обновлении источников, обязательная grounded-проверка, дисклеймер.

2. **Зависимость от платных внешних API и квот.** Yandex SpeechKit — платный (STT ₽0.16/15 сек, TTS ₽1 320/1М символов) без бесплатного лимита; DashScope-модели могут упираться в квоту (реальный инцидент: `qwen-plus` → 403 и потребовалась замена на `qwen3-vl-flash`). При превышении квоты/баланса бот частично деградирует. Митигация: мониторинг квот, запасной `RAG_CHAT_MODEL`, учёт бюджета.

3. **Секреты и безопасность окружения.** Ключи (`.env`) и токен бота не должны попадать в логи/чат — `httpx` логгер заглушён до WARNING именно поэтому; при показе логов токен маскируется. Если ключ скомпрометирован (в учебном проекте отзывать токен не стали) — риск остаётся. Митигация: не выводить `.env` и логи бота наружу, при выходе в продакшен — ротация ключей и секретное хранилище.
