## 1. Цель работы

Реализовать и протестировать в Telegram RAG-боте:
- **краткосрочную память** в виде истории диалога в рамках сессии;

## 2. Архитектура бота

В отличие от монолитного `work_bot.py` из ДЗ_мод5_1, текущая версия использует модульную, слоистую архитектуру, заимствованную из урокового агента:

```
work_bot/
├── work_bot.py              # handlers Telegram + оркестрация
├── rag_engine.py            # retrieval + generation (FAISS, BM25, RRF)
├── dialog_controller/
│   ├── session_manager.py   # управление сессиями и таймаутами
│   └── user_context.py      # краткосрочная память (conversation_history)
└── storage/
    └── user_db.py           # долгосрочная память (facts, JSON)
```

Преимущества такой архитектуры:
- слои заменяются независимо (например, можно поменять хранилище фактов с JSON на SQLite);
- короткая и долгая память не перепутаны с бизнес-логикой Telegram;
- проще тестировать и масштабировать подключение к другим LLM/векторным БД.

## 3. Краткосрочная память

### 3.1 Механизм

Каждый пользователь получает объект `UserContext`. Все сообщения и ответы сохраняются в `conversation_history`. При обработке RAG-запроса:
- для **retrieval** используется только текущий вопрос (или раскрытый follow-up);
- для **LLM** отдельно передаётся история диалога (до 6 сообщений) — модель видит контекст, но поиск не искажается предыдущими темами.

Это позволяет вести многоходовый диалог и задавать уточняющие вопросы, не смешивая разные темы в поиске.

## 4. Сравнение top_k: `/top 3` vs `/top 5`

### 4.1 Зачем менять top_k?

Параметр `top_k` определяет, сколько релевантных чанков передаётся в контекст LLM. При увеличении `top_k` модель видит больше источников и может дать более полный ответ; при уменьшении — ответ концентрируется на самых релевантных фрагментах.

### 4.2 Результаты теста

**Скриншот:** `screens/top3_conosament_with_filo_context.png`

![top3_conosament_with_filo_context.png](screens/top3_conosament_with_filo_context.png)

> Пример «загрязнения» контекста до финального фикса: вопрос `/top 3 что такое коносамент` после диалога про `FILO` получил ответ, в котором смешались и FILO, и коносамент. Причина — слишком широкий детект follow-up и подмешивание предыдущих вопросов пользователя в retrieval-запрос.

**Скриншоты:** `screens/top5_susu.png` и `screens/top3_susu.png`

![top5_susu.png](screens/top5_susu.png)

Наблюдения:

- `/top 3` — footer показывает «Источников в контексте: 3»; ответ короче и содержит только основную расшифровку и ключевые пункты.

- `screens/top3_conosament_clean.png` и `screens/top5_conosament_clean.png` — после фикса ответ только про коносамент.

### 4.3 Улучшения retrieval

Чтобы `/top N` действительно давал разные и более полные ответы, в `rag_engine.py` внесены улучшения:
- **Структурный чанкинг** с детектом заголовков «Статья / Глава / Раздел / § / пункт / markdown #» — чанки получают метаданные `heading` и `article`;
- **Hybrid search**: FAISS dense + BM25 lexical + RRF-фьюжн;
- **Реранкер** `qwen3-rerank` с `RAG_RERANK_MIN_SCORE=0.0`, чтобы не отрезать релевантные чанки;
- **Диверсификация источников** `_diverse_select` — не более 2 чанков из одного документа, чтобы `/top 5` показывал разные источники, а не 5 чанков из одного файла;
- **Перезапись уточняющих вопросов** в `work_bot.py` — follow-up превращается в самостоятельный запрос на основе истории.
- **Plain-text форматирование** — в системный промпт добавлен запрет на markdown, чтобы Telegram не показывал `**`, `#`, `` ` `` как текст. Редкие остаточные markdown-пометки встречаются, но общий вид ответов стал существенно чище (см. скрины диалога выше).

## 5. Долгосрочная память

### 5.1 Механизм

Класс `UserDatabase` хранит факты о пользователях в `user_data.json`. В `handle_rag_qa` добавлена эвристика: если пользователь пишет «Меня зовут …», бот сохраняет имя через `user_db.set_fact(user_id, "name", name)`. При следующих запросах извлечённые факты добавляются в `history_for_llm` и передаются LLM.

## 7. Проблемы и решения

| Проблема | Причина | Решение |
|---|---|---|
| `/top 3` и `/top 5` показывали одинаковые источники | Реранкер с порогом отрезал часть кандидатов, а дедупликация была по имени файла | Включён реранкер с `RAG_RERANK_MIN_SCORE=0.0`, добавлен `_diverse_select` — не более 2 чанков из одного источника, ключ дедупликации учитывает заголовок/сниппет |
| `/ingest` всё время сообщал 103 чанка | Старый FAISS-индекс кэшировался в памяти запущенного бота; инкрементальная индексация не перечитывала файлы, т.к. хеши не изменились | Остановлен бот, удалены `faiss_index.bin`, `metadata.json`, `manifest.json`, выполнена полная переиндексация — теперь 99 чанков |
| `/clear` казалось, что не сбрасывает контекст | Вопросы «А сроки?» понятны и без истории | Добавлена перезапись уточняющих вопросов (`_rewrite_follow_up`) |
| Вопрос `/top 3 что такое коносамент` после диалога про FILO смешал обе темы | Слишком широкий детект follow-up и подмешивание предыдущих вопросов в retrieval-запрос | В `_rewrite_follow_up` исключены самодостаточные вопросы и команды `/top`; в retrieval подаётся только текущий вопрос, история передаётся LLM отдельно |
| Ответы содержали markdown (#, **, `), который Telegram отображал как текст | LLM не получал явного запрета на markdown | В системный промпт и RAG_PROMPT_TEMPLATE добавлено требование использовать plain-text Telegram (только дефисы и цифры для списков, без #, **, *, `, >). Визуальный вид ответов стал существенно чище |
| Качество ответов было низким | Использовалась лёгкая модель `qwen3-vl-flash` | Переключились на `qwen3-max` — ответы стали точнее и полнее |
